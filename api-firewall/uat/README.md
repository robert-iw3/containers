# API Firewall — UAT environment

User-acceptance test for the firewall deployment: a FastAPI mock backend
plays the protected API, the firewall sits in front of it with **every
security layer enabled**, and `run-uat.sh` executes a 25-case battery of
allowed and hostile traffic.

```sh
./run-uat.sh           # full run, tears the stack down afterwards
./run-uat.sh --keep    # leave the stack running on 127.0.0.1:8081
```

Exit code `0` iff all cases pass — CI-friendly.

## How it proves the firewall (and not the app) does the blocking

- **Spec fidelity** — the firewall validates against the OpenAPI 3.0.2
  document exported from the *running* app (`export_spec.py`), so the
  contract under test is exactly what the backend publishes. The spec is
  re-exported on every run; drift restarts the firewall automatically.
- **Unambiguous block marker** — the UAT stack sets
  `APIFW_CUSTOM_BLOCK_STATUS_CODE=418`. The app never returns 418, so
  `418` ⇒ firewall schema/authn block. WAF (Coraza/CRS) denials surface as
  `403` from the rule engine. Anything else came from the app.
- **Backend hit ledger** — the mock app records every request it receives
  (hidden `/_uat/hits` endpoint, excluded from the spec). After the
  negative phase the battery asserts the count did not move: blocked
  requests were rejected at the edge, not proxied and then refused.
- **Permissive app** — the backend deliberately accepts any API key and
  never enforces the denylist; those cases can only pass if the firewall
  enforces them.
- **Response-validation canary** — `/rogue` promises `{"ok": boolean}` in
  the spec but returns a string; the firewall must intercept the response
  (418) even though the request was valid.

## Coverage

| Phase | Cases |
| --- | --- |
| Positive (proxied) | health, list/get/create/update/delete items, documented 404, valid API key |
| Schema violations | wrong types (query + path), min/max bounds, missing required field, numeric constraint, `additionalProperties`, undeclared content type |
| Unknown surface | unknown path, undeclared method, hidden `/_uat/*` endpoints |
| Authn | missing required API key, denylisted token |
| WAF (CRS 4.x) | scanner detection (sqlmap UA), XSS payload inside a schema-valid string field |
| Response validation | app response violating the declared schema |
| Invariant | backend hit-count unchanged across all blocked requests |

## Notes / findings baked into the deployment

- The firewall's kin-openapi parser rejects OpenAPI 3.1 constructs (e.g.
  numeric `exclusiveMinimum`); the mock pins FastAPI 0.98/pydantic v1 to
  emit clean 3.0.2. Keep this in mind for real backends generated by
  modern FastAPI.
- Stock CRS only allows `GET HEAD POST OPTIONS`; `config/coraza.conf` now
  sets rule 900200 (`tx.allowed_methods`) to the full REST verb set —
  discovered when PUT/DELETE UAT cases came back 403 from rule 911100.
- CRS content-type policy fires before schema validation, so an undeclared
  `text/plain` body is a WAF 403, not a schema 418 — layering works
  outside-in.
